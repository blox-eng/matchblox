# matchblox v0.1: the front door

Status: accepted (2026-10-06). Language: ASD-STE100. Code names stay as they
are.

This document changes `0001-v0.1.md`. Where the two do not agree, this
document applies. Plan `0004-v0.1-plan.md` replaces the open milestones (3 to
8) of plan `0002-v0.1-plan.md`.

## 1. Purpose

A builder installs matchblox and has a working control pane for every agent in
less than one minute. The first user is the builder who makes matchblox: one
host, about 20 Claude Code sessions in tmux, a desktop terminal, and a phone or
tablet over SSH. If v0.1 works for that builder every day, it is ready for
other builders.

## 3. The control pane

The builder opens a terminal app (for example, Termius on a phone) and
connects to the host. The console is the first screen. The builder sees who
waits, the context of each session and the machine load, and goes into a pane
and back without tmux keys.

1. `matchblox` outside tmux, with tmux installed, runs the console in its own
   tmux session `matchblox`: `tmux new-session -A -s matchblox matchblox`. A
   second connection attaches to the same session.
2. A terminal app can run `matchblox` when it connects. The docs show this for
   Termius (startup snippet) and for `ssh -t host matchblox`.
3. `Enter` on a session or a queue row switches the tmux client to that pane.
4. **The way back** is one tap or one key:
   - a tap on `◂ matchblox` at the left of the tmux status line, and
   - the tmux prefix and then `m`.
   Setup adds both to `~/.tmux.conf` after a confirm and keeps a backup
   (§6, door 3).
5. Below 60 columns the console uses the phone layout of 0001 §10.3: the queue
   first, two lines for each row, a tap selects, a second tap runs the safe
   action.

## 4. The mark in the console

1. **Start screen.** The isometric matchbox from the site, drawn with
   half-block characters (two pixels in each cell) in the colour tokens of
   0001 §10.1. The blocks fall into a box, the drawer opens, the match
   strikes. In a dark terminal the match burns. In a light terminal it stays
   unlit. It takes less than 600 ms. Any key stops it. `--no-motion` and
   `NO_MOTION=1` show the last frame only.
2. The start screen stays while the console waits for the service, in place
   of "waiting for the service…".
3. **Header.** The left of the header shows a one-cell mark, the name and the
   host: `▰ matchblox · ws-1`. Remote mode needs the host name there, too.
4. The service sends its host name in `hello`. On fixtures, the host name
   comes from `<fixtures>/proc/sys/kernel/hostname`, so a demo or a test never
   shows the name of the real machine.

5. **A match for each session** (owner, 2026-10-07). Each session row, in
   the console and in the replay, starts with a one-cell match: `✦` burning
   while the agent works, `╿` at rest while it waits for the person (its
   head breathes when it asks), `│` spent when its context is at or above
   the compact limit. Spent comes first, the state word stays, and a change
   plays once (the strike). The glyphs, colours and motions are in
   `DESIGN.md` §4, which is binding.

## 5. The stoker (was: night mode)

Amended 2026-10-09 (owner): the stoker is the engine, and a night is a
stoker run with an end. `docs/stoker.md` is the reference; DESIGN.md §6 has
the layout.

1. `f` turns the stoker on or off; `n` starts a night that ends at
   `[stoker] night_ends` (07:00). The header shows `stoker` or
   `night → 07:00`. The service keeps the mode in `stoker.json` across a
   console and a service restart.
2. While it is on, the service runs one rule step after each sample:
   - **Compact.** A Claude Code session that is idle (and not cold: idle
     under 24 h), at or above the compact limit and not waiting for the
     builder gets `/compact` with this instruction: "Keep the task, the
     branch and last commit, the files you changed, what to read first,
     every open decision and the next step. End with one line that starts
     with RESUME: and says how to continue." The runner's idle guard is
     checked right before the send.
   - Nothing else. A destructive step from any other rule waits for a
     person, as in the day. A rule joins the stoker only when it is decided
     from measured state, re-checked on the host before the send, answers
     nothing, is not destructive and leaves evidence.
3. The stoker never answers a question or a permission prompt, and never
   sends "continue". A session that waits stays in the queue.
4. Each step goes to `~/.local/state/matchblox/stoker.jsonl`: the time, the
   session, the rule, the argv, the guard, the result, the context before
   and after (from the compact boundary) and the RESUME line.
5. **The return.** While a run has steps the builder has not seen, the
   console shows STOKED above the queue: each step with its evidence and
   RESUME line. `Enter` folds it.
6. A limit: at most one step for each session for each 30 min, and at most
   30 steps for each run. Codex and OpenCode stay out: their `/compact`
   takes no instruction.

## 6. Setup as doors

The first run shows the machine at once. Setup is a list of doors. Each door
is one row with one action. A door that is done folds away.

1. The install script, when a terminal is attached, starts `matchblox` and
   gives it the terminal (`</dev/tty`). Without a terminal, it prints
   "run: matchblox".
2. On the first run (no config file), the start screen plays, the service
   starts, and the console shows the machine with the doors above the queue.
3. The doors, in this order. Each one shows what it will change before it
   changes anything:
   1. **tmux.** If tmux is missing: the exact install command for the OS and
      package manager (`brew install tmux`, `sudo apt install tmux`,
      `sudo dnf install tmux`, `sudo pacman -S tmux`). It runs after a
      confirm, in the terminal, so the password prompt is the builder's own.
   2. **The queue.** Add the hooks (Notification, Stop, UserPromptSubmit,
      SessionStart, SessionEnd, PostToolUse) to `~/.claude/settings.json`
      (`$CLAUDE_CONFIG_DIR` when set). The door shows the diff, writes after
      a typed `y`, and keeps a backup. Values it does not change keep their
      bytes, so the diff shows only the new lines.
   3. **The way back.** Add the status-line tap and `prefix m` to
      `~/.tmux.conf` (§3). Same rules: diff, confirm, backup, then
      `tmux source-file`.
   4. **Hosts.** Replaced by the first-run question and the Hosts layer of
      remote mode (#23, design/0005-remote-mode.md): hosts are not a door.
   5. **Night mode.** One sentence on what it does, and `n` to try it.
      (Ships with night mode, #24, for the same reason.)
   6. **A guide session** (optional). Open one tmux window that runs Claude
      Code with a first prompt that points to the docs' getting-started page.
      It is never opened without a confirm: it spends the builder's tokens.
4. Thresholds come from the machine (core count, RAM). Setup does not ask
   for them. The config file holds them for a builder who wants to change
   them.
5. `matchblox setup` shows the same doors as a short form (huh), for a
   builder who wants them all at once.
6. Setup writes `~/.config/matchblox/config.toml`. It never writes a file
   outside `~/.config/matchblox/` without a confirm and a backup.

## 7. The replay

1. `testdata/demo/` is a generic machine: host `ws-1`, a few Claude Code
   sessions in tmux, one session near its compact limit, one detached busy
   loop.
2. A Go test in `cmd/matchblox` runs the real service and the real console
   in one process, on `testdata/demo`, at a fixed size and with a fixed clock.
   It sends a key script and keeps each frame that changed.
3. The demo service gets a demo host: CPU counters that move, and a busy
   loop that goes away when the kill step runs. The kill does not run on the
   real machine.
4. With `-update`, the test writes `www/demo/frames.json` (for the site) and
   `www/demo/replay.svg` (an animated SVG for the README, which follows light
   and dark). Without `-update`, it fails when the files are out of date. CI
   runs it, so CI fails when the console fails.
5. The replay shows only what works. Re-record it when the queue, night mode
   and the doors ship.

## 8. The site and the repository

1. matchblox.com follows issue #9, with two changes:
   - The replay comes after the hero (the line and one sentence), not
     before it. (Owner, 2026-10-06.)
   - The footer says "From Blox Engineering" and links GitHub, Discord, the
     docs and bloxng.com. It does not link goifc.org or openblox.sh.
2. The repository files are the first page many builders see. Each one is
   short, exact and current:
   - **README**: the replay, the line, one install command, a three-step
     quick start, what it shows, the keys, the control pane from a phone,
     safety, config, links. It says only what works in the release.
   - **CONTRIBUTING**: the dev loop (`go test ./...`, `scripts/validate.sh`),
     TDD, Conventional Commits, the fixture rule (no real machine, person or
     company), and how to record the replay again.
   - **SECURITY**: private reports through GitHub security advisories, what
     is in scope (the service socket, guards, the hook command, the install
     script), and the response time.
   - **CODE_OF_CONDUCT**: keep it, and make sure it names how to report in
     private.
   - **LICENSE**: MIT, "Copyright (c) 2026 Blox Engineering" (no change).
   - **The pull request template**: lists only the checks that CI does not
     do.

## 9. Not in v0.1 (issues)

## 10. Done when

- The builder connects from a phone and the console is the first screen. A
  tap goes into a pane, one tap comes back.
- Night mode runs a night on the builder's host. In the morning, "Overnight"
  lists each compact with its RESUME line, and the queue.
- A new user goes from the curl command to a working console with hooks in
  less than one minute.
- The console start screen shows the mark, and the header shows the host.
- CI records the replay from the real console, and the README and the site
  show it.
