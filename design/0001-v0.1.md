# matchblox v0.1 — design

Status: approved for planning, 2026-10-06.
Language: ASD-STE100 Simplified Technical English. Code names stay as they are.

## 1. Purpose

**A tool for modern software builders.** Motto: **Light the match. Keep it burning.**

matchblox is a terminal console for a person who runs many AI coding agents at
the same time. It shows which agent needs the person now. It shows the load on
the machine, the state of each git checkout, and what to do next. It lets the
person go to a pane, answer an agent, or do a safe action with one key.

The person must feel more able, not more watched. The console must be fast,
quiet and exact.

## 2. Success criteria

1. A new user installs matchblox with one command and answers a short setup in
   less than two minutes.
2. The "waiting for you" queue shows an agent that stops or asks for permission
   in less than one second.
3. The same console works in three ways, with the same keys and the same data:
   - on the host itself,
   - over SSH from any terminal app (for example, a phone or tablet SSH app),
   - on a laptop that connects to a host over SSH (remote mode).
4. The service uses less than 1% of one CPU core when the machine is idle.
5. No action runs without its exact command on the screen. No destructive
   action runs without a typed confirm.

## 3. Scope

### 3.1 In v0.1

- **Sessions, Machine, Procs, Git, Recs, History.** These panels come from
  `builder-tui` without loss of function.
- **Waiting for you.** A queue at the top of the screen. It lists each agent
  session that stopped, that asks a question, or that asks for permission. The
  oldest wait is first.
- **All panes.** A list of all tmux panes, not only agent panes. The person can
  go to a pane, or send text and keys to a pane after a confirm.
- **Remote mode.** The console on a laptop shows a host over SSH.
- **Pilot.** An optional AI assistant through OpenRouter. It reads the state and
  makes recommendations. It has three modes: off, suggest, auto.
- **Install and setup.** One install command, a Homebrew tap, and a first-run
  setup with questions.
- **Motion.** A short start animation and a small set of named motions.
- **Sites.** A landing page on matchblox.com and docs on docs.matchblox.com.

### 3.2 Not in v0.1 (GitHub issues)

1. Subagent monitoring: each subagent, its task, its tokens and its time.
2. Usage limits: weekly and 5-hour use, burn rate, and a forecast of the cap.
3. Pull requests and CI for each worktree, with open, rerun and remove actions.
4. Old dev servers: a long-running server in a worktree whose branch merged.
5. Code graph freshness for each checkout, with the reindex command.
6. Cost for each session for each day.
7. Pilot auto mode for destructive steps, with an allowlist.
8. More than one host on one screen.
9. Native Windows sessions (WSL works in v0.1).
10. More agents than Claude Code (for example, Codex), through the agent adapter.
11. More multiplexers than tmux (for example, zellij), through the pane interface.

## 4. Architecture

### 4.1 Units

Each unit has one job. A unit talks to other units only through its interface.

| Unit | Job | Interface |
|---|---|---|
| `host` | Read CPU, memory, swap, load, pressure, disks, network, processes. Linux reads `/proc` and `/sys`. macOS and Windows use the system APIs. | `Host` |
| `agents` | Find agent sessions, read context use and state. One adapter for each agent. Claude Code is the first. | `Agent` |
| `panes` | List, capture, send to and switch to terminal panes. tmux is the first. | `Mux` |
| `gitscan` | Read checkouts, worktrees, dirty paths, behind counts, merged branches. | `Scanner` |
| `advice` | Change state into a ranked list of recommendations. Each item has evidence and an action. | `Build(state) []Rec` |
| `actions` | Hold argv steps and their guards. Check each guard again just before its step. Run the step. | `Runner` |
| `hooks` | Receive agent hook events and keep the queue. | `Inbox` |
| `pilot` | Send state to a model, receive proposals, apply the mode policy, write the audit log. | `Provider`, `Policy` |
| `service` | Own every loop, the state and the event stream. | `Service` |
| `proto` | Define the messages between the service and the app. | versioned types |
| `transport` | Carry messages: a local socket, or stdio over SSH. | `Conn` |
| `app` | Keep a copy of the state from the transport. Draw it. Send action requests. | Bubble Tea model |
| `theme` | Hold the colour tokens, the type rules and the motions. | `Theme` |
| `setup` | Ask the setup questions and write the config. | `huh` forms |

### 4.2 Rules

1. The app does not read the machine. It draws only what it receives from the
   service.
2. The service does not import the app.
3. Every step runs on the host of the service. Every guard is checked there.
4. No unit builds a shell string from data. Steps are argv lists.

### 4.3 One binary

| Command | Function |
|---|---|
| `matchblox` | Open the console. Connect to the local service, or start it. |
| `matchblox <host>` | Open the console for a host over SSH (remote mode). |
| `matchblox serve` | Run the service. `--stdio` speaks on stdin and stdout. |
| `matchblox setup` | Run the setup again. |
| `matchblox status [--text]` | Print the state as JSON, or as a short text, for scripts and agents. |
| `matchblox hook <event>` | Receive one agent hook event. Agents call this. |
| `matchblox version` | Print the version. |

## 5. Run modes

### 5.1 On the host

1. `matchblox` looks for the service socket in `$XDG_RUNTIME_DIR/matchblox/`.
2. If no service runs, `matchblox` starts `matchblox serve` in the background.
3. The service continues when the console closes. History, the queue and the
   pilot do not stop.

### 5.2 Over SSH from any terminal app

The person connects to the host with SSH and types `matchblox`. This is the
same as 5.1. The console needs nothing from the terminal app.

To go to a pane:

- If the console runs inside tmux, `Enter` switches the tmux client to the pane.
  One key goes back to the console.
- If the console runs outside tmux, `Enter` attaches to the pane. When the
  person detaches, the console comes back.

### 5.3 Remote mode

1. The person types `matchblox <host>` on the laptop. `<host>` is a name from
   `~/.ssh/config`.
2. The console runs `ssh <host> matchblox serve --stdio`. SSH keys, jump hosts
   and agents from the user's SSH config apply.
3. `serve --stdio` connects to the service on the host, or starts it.
4. If matchblox is not on the host, the console asks to install it there. It
   uses the install script for the host's OS and CPU.
5. To go to a pane, the console opens a new terminal tab with
   `ssh -t <host> tmux attach -t <pane>`. With kitty remote control, it uses
   `kitty @ launch`. Without it, the console gives the screen to SSH and comes
   back after the person detaches.

## 6. Protocol

- Newline-delimited JSON. One message on each line.
- The first message from each side is `hello`, with the protocol version. If
  the major version is different, the console shows the fix: the command that
  updates matchblox on the host.
- Message kinds:
  - `snapshot`: the full state, at connect and at each sample.
  - `event`: a hook event, an alert, a pilot proposal, a queue change.
  - `act`: an action request from the app (step id, confirm token).
  - `result`: the result of an action, with output and a guard failure if any.
  - `pilot`: a mode change from the app.

## 7. Waiting for you

### 7.1 Source

Setup asks to add hooks to `~/.claude/settings.json`. Each hook calls
`matchblox hook <event>`. The command writes the event to the service socket
and stops in less than 50 ms. If the service does not run, the command writes
the event to a spool file and stops. The service reads the spool when it
starts.

| Hook event | Queue state |
|---|---|
| `Notification` (permission) | asks for permission |
| `Notification` (idle prompt) | waits for input |
| `Stop` | finished its turn |
| `UserPromptSubmit` | working (leaves the queue) |
| `SessionStart`, `SessionEnd` | appears, disappears |

Without hooks, the console guesses the state from CPU use and the transcript,
as `builder-tui` does. The queue then shows "estimated".

### 7.2 Display

- Each row shows: the glyph and the state word, the wait time, the session
  name, the tmux place, and the last line the agent wrote.
- `Enter` goes to the pane. `a` sends a short answer after a confirm.

## 8. Pilot

### 8.1 Modes

| Mode | Behaviour |
|---|---|
| off | The pilot sends nothing. This is the default. |
| suggest | The pilot ranks what needs the person and why. Each proposal shows its exact steps. Nothing runs until the person presses `Enter`. |
| auto | The pilot runs a step only when the step is safe and the allowlist contains it. A destructive step always waits for `x` then `y`. |

`p` changes the mode. The status line always shows the mode.

### 8.2 Data

- The pilot sends the snapshot and the queue. It sends the text of a pane only
  when the person opted in for that pane.
- Before it sends text, the pilot removes strings that look like secrets:
  tokens, keys, passwords, and long base64 or hex strings.
- The OpenRouter key is in the OS keychain on macOS, or in
  `~/.config/matchblox/openrouter.key` with mode 0600.
- The person chooses the model in setup. The pilot sets a request limit for
  each hour.

### 8.3 Audit

Each proposal and each step goes to `~/.local/state/matchblox/pilot.jsonl`. A
line holds the time, the mode, the pane, the input digest, the model, the reply
and the steps. The console shows the last entries.

## 9. Safety

1. The console is read-only by default.
2. Each action shows its exact argv before it runs.
3. `Enter` runs only non-destructive steps.
4. A destructive step needs `x` and then a typed `y`. Any other key cancels.
5. Each step has a guard. The service checks the guard just before the step:
   - the same pid with the same start time,
   - a worktree that is still clean and has no process in it,
   - a session that is still idle.
   If a guard fails, the service does not run the step and tells why.
6. Steps run with a time limit, no terminal prompts, and SSH in batch mode.
7. The service and every step run at the lowest CPU priority.

## 10. Look and feel

### 10.1 Colour

Dark first. A light set applies when the terminal background is light.

| Token | Dark | Light | Use |
|---|---|---|---|
| bg | `#0F0D0A` | `#F5F1E7` | background |
| fg | `#EBE6DC` | `#1C1813` | text |
| muted | `#A69D8D` | `#5F5A4C` | secondary text |
| faint | `#918770` | `#6C6352` | labels, units |
| hair | `#2A251C` | `#DAD2BF` | hairlines |
| accent | `#C3A56A` | `#9A7B3F` | active tab rule, selection, the one primary action |
| warn | `#B98F44` | `#8A6420` | warnings |
| neg | `#B0563F` | `#9E4A34` | failures, destructive actions |

Rules:

1. The accent appears once in each view.
2. A region is a small uppercase label, a hairline and space. Panels have no
   boxes.
3. Tabs are one row. The active tab has an accent rule under it.
4. A status is a glyph and a word: `✓ idle`, `! waiting 4m`, `▲ 92 °C`. Only an
   exception gets a colour wash. A normal row stays quiet.
5. Figures are aligned. Units are faint.
6. An empty state is one sentence and the action that resolves it.
7. An error tells the fix.
8. `/` opens search. Search is not on the screen until then.

### 10.2 Motion

The work of the system is silent. The act of the person has weight.

| Motion | Time | Use |
|---|---|---|
| Fade | 140 ms | new values, menus |
| Rise | 180 ms | the confirm bar, toasts |
| Fall | 520 ms | the start animation (the match strikes) |
| Stamp | 240 ms | a confirmed destructive action |
| Heal | 240 ms | a corrected figure shows "was X" |
| Pulse | 1.6 s | a value that is not measured yet |

There are no spinners. The start animation is less than 600 ms, and any key
stops it. `--no-motion` or `NO_MOTION=1` makes every motion an instant change.

### 10.3 Layout

- 100 columns or more: all columns, side detail.
- 60 to 99 columns: fewer columns, detail under the list.
- Less than 60 columns (phone): one column, the queue first, each row on two
  lines. A tap selects a row. A second tap runs its safe action.
- Every key is on a phone SSH key bar: digits, arrows, `Enter`, `Esc` and
  letters. No `Ctrl` combinations.

## 11. Install and setup

### 11.1 Install

- `curl -fsSL https://matchblox.com/install.sh | sh`
  - The script is one function, so a partial download does nothing.
  - It installs the binary for the OS and CPU, checks its SHA-256, and checks
    the provenance when `gh` is installed.
  - It installs to `/usr/local/bin`, or to `~/.local/bin` when the first is not
    writable. `MATCHBLOX_VERSION` selects a version.
- `brew install blox-eng/tap/matchblox`
- `go install github.com/blox-eng/matchblox/cmd/matchblox@latest`

### 11.2 Setup

The first run starts the setup. Each question has a default from the machine.

1. Which agents do you use? (Claude Code is found automatically.)
2. Add hooks for the "waiting for you" queue? (yes)
3. Which hosts do you want to see? (names from `~/.ssh/config`)
4. Turn on the pilot? If yes: the OpenRouter key, the model, the mode.
5. Thresholds: temperature, load, pressure, memory, swap. (defaults from the
   machine)

Setup writes `~/.config/matchblox/config.toml`. It changes
`~/.claude/settings.json` only after a confirm, and it keeps a backup.

## 12. Performance budget

| Item | Limit |
|---|---|
| Service, idle machine | < 1% of one core, < 40 MB RSS |
| Console, idle | < 0.5% of one core |
| Hook command | < 50 ms |
| Queue update after a hook | < 1 s |
| Start to first frame | < 300 ms (animation runs over it) |

Cadence: cheap counters every 2 s, processes every 10 s, containers and GPUs
every 60 s, git every 5 min. The renderer runs at 15 frames each second or
less, and only when something changes.

## 13. Repository, release and sites

- `blox-eng/matchblox`, public, MIT, "Copyright (c) 2026 Blox Engineering".
- The code starts from `builder-tui` (Lutherwaves/builder#15) with a new
  history. builder#15 closes with a link here. The `tui` skill in builder
  becomes a small skill that installs matchblox.
- CI: conventional commits, gofmt, vet, golangci-lint, tests, govulncheck,
  CodeQL, cross-builds. Actions are pinned by SHA.
- Release: go-semantic-release after CI passes on `main`. Binaries for linux
  and darwin on amd64 and arm64, `.sha256` files, SBOMs, Sigstore attestations.
  The Homebrew formula updates in `blox-eng/homebrew-tap`.
- Changelog: entries go under `## [Unreleased]`. After a release, a bot pull
  request moves them under the version and merges itself. A guard fails other
  pull requests until that pull request merges.
- matchblox.com: a static `www/` on Cloudflare. The first view is the console
  itself, a replay of a demo machine. Then the line "A tool for modern software
  builders.", the install command, three short blocks, the motto "Light the match. Keep it
  burning.", and links. The footer says "From Blox Engineering" and links
  the other tools for builders (goifc.org, openblox.sh) and bloxng.com.
- Voice: every page, the README and the docs use the same line and motto. The
  sentences are short and say what the person gets. The matchbox mark has a
  small animation, and it is the theme switch: to go dark, the box opens, the
  match rises, strikes on the side of the box and burns; to go light, the flame
  goes out and the match goes back in the box. Under reduced motion the theme
  changes with no motion.
- docs.matchblox.com: MkDocs Material on GitHub Pages, versioned with mike.
- The repository contains no details of a real machine, person or company.
  Demo data and test data are generic.

## 14. Testing

1. Unit tests for each unit against fixtures: a fake `/proc`, `/sys`, home and
   tmux list.
2. Protocol round trip: the app talks to `serve --stdio` through a pipe.
3. Hooks: events in, queue states out, spool replay.
4. Pilot: a fake OpenRouter server. Tests check each mode, the secret filter,
   the allowlist and the audit log.
5. Safety: `Enter` never runs a destructive step. A failed guard stops its step.
6. Setup: the forms run without a terminal and write the expected config.
7. Layout: golden frames at 50, 80 and 120 columns.
8. The landing replay is a VHS recording of the demo machine. It also runs as
   an end-to-end smoke test in CI.
9. Performance: a test measures idle CPU of the service for 60 s.
