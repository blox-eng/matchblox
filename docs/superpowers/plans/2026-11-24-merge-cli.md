# Plan: merge a waiting ship from the CLI

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A builder (or agent) runs `matchblox merge <who>` and merges the same leading ship board `p` would, through the existing guarded `ship:` act.

**Architecture:** Add a CLI twin beside `kill`/`rename` in `cmd/matchblox`. Resolve `<who>` with existing `resolve`, pick the leading ship with existing `shipOf` / `ships.Of`, refuse with the board's words when it does not wait, else send `proto.Act{RecID: "ship:<repo>#<n>", Which: "secondary", Confirm: "y"}` through `doAct`. The service already re-checks `WaitsForYou` + `Merge` in `resolve`. Invent no `gh` argv in the CLI.

**Tech Stack:** Go, existing `cmd/matchblox` CLI + `internal/service` ship acts + `internal/ships`.

**Spec:** docs/superpowers/specs/2026-11-24-merge-cli-design.md

## Global Constraints

- Command shape is `matchblox merge <who>` (C1), twin of board `p`.
- Refusal words: `no ship of <name> waits for a merge` (exact board notice).
- Do not invent `gh pr merge` argv; only the Ships report's `Merge`.
- No new confirm prompt on the CLI (life commands already send `Confirm: "y"`).
- No phone buzz, stale-host cue, Pocket jump, bulk merge, or ADE surface.
- Feat PR body: `Landing page: unchanged because the merge CLI is a headless twin of board p, not a marketing story change.`
- Conventional Commits; no WIP; no `--no-verify`.

## Review Focus

1. Leading ship is Stuck (or Running) while another ship waits — expect refuse on leading-only rule; Task 1 pins it.
2. `WaitsForYou` with empty `Merge` (stale green / unread) — expect refuse, no invented argv; Task 1.
3. Wrong `Which` or missing `Confirm` — expect service refuse; Task 1 asserts act fields; service already covered in `TestShipsReachTheState`.
4. Unknown `<who>` — same resolve error as kill; Task 1.
5. Second merge after success — expect refuse; Task 1 with Kind not waiting / empty Merge.

## Lens findings

**Engineering**
- Reuse `resolve`, `shipOf`, `doAct`, `handOutcome`, service `ship:` resolve — no new module. No change, because eight files would be a smell; this stays in `cmd/matchblox` + docs.
- Failure in production: Ships report lags and `Merge` empties while Kind still says waits — Task 1 empty-Merge refusal; service also refuses empty Merge.
- Regression: `kill`/`rename`/`ships` paths untouched; existing life tests keep them.
- Scale: one resolve + one ship lookup per invoke. Fine.

**Design**
- Empty/refuse: `no ship of <name> waits for a merge` — Task 1 asserts exact words. Rating 9→10 if name is the session's Name (plan uses that).
- Success: quiet like kill (handOutcome). No change, because spec allows quiet success.
- Error when service down: existing `errNotRunning` via `readDoc`. No new copy.

**Architecture (agent tool)**
- Tool risk: dangerous write. Guard is service `WaitsForYou` + non-empty `Merge` plus CLI pre-check. Task 1 hostile tests are the guard. No change to service contract.
- Contract lives in `-h` + `docs/ships.md` next to the command (project's rule).
